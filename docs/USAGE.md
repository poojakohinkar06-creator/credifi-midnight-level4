# CrediFi — Usage Guide

How to run and use the current CrediFi MVP on **Midnight Preprod**. Everything
below describes behaviour that exists in this repository; anything the code does
*not* do is called out explicitly.

- **Test users:** [`USERS.md`](../USERS.md)
- **Feedback:** [`docs/FEEDBACK.md`](./FEEDBACK.md)
- **Setup details:** [`docs/setup.md`](./setup.md)

---

## Prerequisites

- **Node.js ≥ 22** and npm (declared in `package.json` `engines`).
- A **Midnight-compatible browser wallet** — 1AM Wallet is the one used in the
  Level 5 test round.
- A Chromium-family browser, because 1AM Wallet is a Chrome extension.

---

## 1. Install 1AM Wallet

- **Official website:** <https://1am.xyz/>
- **Chrome Web Store:**
  [1AM Wallet](https://chromewebstore.google.com/detail/1am/bphnkdkcnfhompoegfpgnkidcjfbojjp)

Install the extension and create/open a wallet in it. CrediFi does not need a
funded Preprod account for the eligibility flow — the wallet is used for
identity and network, not for paying fees (see
[On-chain submission](#on-chain-submission-still-deferred) below).

---

## 2. Switch the wallet to Midnight Preprod

CrediFi hard-requires the **Preprod** network:

```ts
// frontend/src/config.ts
export const NETWORK_ID = "preprod" as const;
```

`connectWallet()` calls `connector.connect(NETWORK_ID)` and then compares the
network the wallet actually reports against `NETWORK_ID`
(`frontend/src/wallet.ts:149` and `frontend/src/wallet.ts:172`). If they do not
match, the connection is rejected with a `wrong-network` error and the UI shows
*"Wrong network: the wallet is on …, but CrediFi requires Midnight Preprod.
Please switch the wallet to Preprod and try again."*

So: **switch the network inside 1AM Wallet before pressing "Connect wallet".**

---

## 3. Start the CrediFi app

CrediFi is a **locally-run web app**, not a hosted site. The README documents
this exact command sequence:

```bash
npm install
npm run contract:compile   # regenerates the managed bindings + zkir artifacts
npm run frontend:dev       # http://localhost:5173
```

`npm run contract:compile` is required on a fresh clone because
`contract/src/managed/` is generated by the Compact compiler. Open
<http://localhost:5173> in the same browser that has 1AM Wallet installed.

Optional checks, from the README:

```bash
npm run contract:test    # 30 contract tests
npm run frontend:test    # 59 frontend tests
```

---

## 4. Connect 1AM Wallet

Click **Connect wallet** in the navbar (or the button on the home page hero, or
the **Connect wallet** button in the *Connect wallet* panel on the
*Check Eligibility* page).

How it works, from `frontend/src/wallet.ts`:

1. **Connector discovery by enumeration.** `detectWallet()` looks for
   `window.midnight` and enumerates every entry, keeping the ones that look like
   a connector (an object with a `connect` function and a `name` string). Lace is
   only preferred as a tie-break (`wallet.ts:56-79`). This is why 1AM Wallet
   works without being hard-coded.
2. **Real approval.** `connector.connect(NETWORK_ID)` is invoked **synchronously
   from the click handler** so the browser does not block the wallet's
   authorisation popup (`wallet.ts:134-149`). You approve the request in 1AM
   Wallet.
3. **Address read.** The app reads the **shielded address** first and falls back
   to the unshielded address if the shielded read is unavailable
   (`wallet.ts:116-126`). The navbar shows a shortened form of it.
4. **Connection state is never faked.** The app only marks itself connected
   after the wallet approves and reports a real address and network. A mocked
   connector exists **only** inside `frontend/src/test/App.test.tsx` and is never
   used in the browser flow.

Once connected, the Dashboard, History and Certificate nav items become
available.

## 5. Complete eligibility verification

The flow lives on the **Check Eligibility** page and is presented as four steps by
`frontend/src/components/ProgressSteps.tsx`:

- **Step 1 — Financial Information.** Two cards side by side:
  - *Your Financial Details* (`CredentialCard.tsx`): **Monthly Income**
    (number input, `min={0}`, `max={65535}`) and **Previous Loan Default?**
    (Yes / No). These are your **private witness values**.
  - *Choose your loan requirement* (`RequirementForm.tsx`): three preset
    minimum-income cards (₹25,000+, ₹50,000+, ₹1,00,000+), plus an expandable
    *"Enter an exact amount or adjust lender settings"* section for a custom
    minimum income, the **no prior default** requirement, and a **lender
    reference** (defaults to `Midnight Lending Co` in
    `frontend/src/config.ts`). Press **Continue →**.
- **Step 2 — Verification / Step 3 — Generate Proof.** Press **Check
  Eligibility**. A phase list cycles every 450 ms through *"Connecting wallet…"*,
  *"Preparing verification…"*, *"Generating privacy proof…"*, *"Waiting for
  blockchain confirmation…"*, and the app deliberately pauses ~1 s so the
  processing state is visible (`App.tsx:143`).
- **Step 4 — Result.**

### How the result is actually computed

This matters for reading the rest of this guide correctly. The result is **not**
mocked and **not** produced by a hard-coded branch: `CrediFiEngine.verify()`
(`frontend/src/engine.ts:93-144`) executes the **officially compiled CrediFi
Compact contract** in-process (vanilla execution, the same path the contract unit
tests use), then **reads the record back out of ledger state** and throws if the
record is absent (`engine.ts:123-128`). The returned outcome contains no income
figure.

Note that the *"Waiting for blockchain confirmation…"* phase is **presentation
only**. Nothing is submitted to Midnight in the browser during this step.

---

## 6. Read the eligibility result

Two things appear at once:

- A **notification** at the top of the page: *"🎉 Congratulations! You are
  Eligible."* or *"Sorry, You are Not Eligible."* (`lib/navigation.ts:48-62`),
  announced via `aria-live` and auto-dismissed after 9 seconds.
- The **result panel** in Step 4 (`EligibilityResult.tsx`): an **Eligible** /
  **Not Eligible** hero, a requirement-match card showing which conditions were
  met or unmet, and a disclosure of how the result was computed.

The unmet conditions come from the real contract outcome fields
(`lib/eligibility.ts`), and are limited to the lender's own two requirements:

| Label | Meaning |
| --- | --- |
| Income threshold met | `incomeSatisfied` is true |
| No prior-default condition met | `defaultRequirementSatisfied` is true, or the lender did not ask for it |
| Income threshold not met | `incomeSatisfied` is false |
| Prior default on record | the lender required a clean history and it was not satisfied |

Your **exact income and default flag are never displayed as part of the result**,
because the compiled contract only produces these boolean outcomes.

Actions available on the result: **Start over** (resets the form to its
defaults), **View Dashboard**, and **Get Certificate**.

---

## 7. Dashboard

Open **Dashboard** in the navbar, or the **Check Eligibility** button on the
Overview tab. The Dashboard is available **as soon as a wallet is connected**
(`App.tsx:72`) and renders honest empty states until a verification has actually
run — it never fabricates a result.

`frontend/src/components/Dashboard.tsx` shows:

- **Four stat cards** (`Dashboard.tsx:23-52`): **Wallet** (shortened address,
  *Connected* / *Not verified*), **Eligibility** (*Eligible* / *Not Eligible* /
  *—*), **Verifications** (count this session), **Network** (*Midnight Preprod*).
- **Verification status** card — the latest result, referencing the result id and
  lender reference.
- **Privacy status** card — states that exact income and history never appear in
  the dashboard or on-chain.
- **Recent verification activity** — the most recent check with its requirement.
- A **risk category** line, but be careful here: the contract does **not**
  compute a numeric risk score. `lib/eligibility.ts` deliberately derives a plain
  language category from the boolean outcome fields (*Eligible*, *Income
  Threshold Not Met*, *Clean-History Requirement Not Met*, *Not Eligible*) and
  never invents a score.

## 8. Verification History

Open the **History** nav item or the **History** dashboard tab
(`frontend/src/components/VerificationHistory.tsx`).

> ### ⚠️ History is session-only — it is not persisted
>
> Verification history lives in a single React `useState` array in
> `frontend/src/App.tsx:61`:
>
> ```ts
> const [history, setHistory] = useState<VerificationOutcome[]>([]);
> ```
>
> Each successful verification appends to it (`App.tsx:150`). There is **no**
> `localStorage`, no IndexedDB, no backend call and no on-chain read-back that
> repopulates it. **Every result is lost when the page is reloaded or the tab is
> closed.** `Disconnect wallet` clears the current outcome and returns the user
> to the setup screen but does *not* clear the history array, so the list
> survives a disconnect within the same page session (`App.tsx:102-110`). The
> component says so in its own copy: *"N checks recorded in this session"*
> (`VerificationHistory.tsx:32`), and the Dashboard likewise says *"Nothing
> recorded yet this session"* (`Dashboard.tsx:161`).
>
> The README lists *"Persistent verification history across sessions"* under
> **Roadmap / deferred**, so this is a known open item, not a defect being hidden.
> Do not expect your past results to still be there after a refresh.

When history is non-empty, each row shows the requirement (*Min income* and, if
requested, *no prior default*), the result, the status, and an expandable
**Technical details** block with the lender reference, result id and a truncated
holder hash.

---

## 9. Eligibility Certificate

Open the **Certificate** nav item or the **Certificate** dashboard tab
(`frontend/src/components/EligibilityCertificate.tsx`).

- If no verification has been run yet, the tab shows *"Run a verification to
  generate a certificate."* (`App.tsx:343`).
- The certificate summarises the **requirement**, the **eligibility status**,
  the **lender reference**, the **result id**, a truncated **holder** hash
  (16 characters + `…`), how the result was **computed**, and the explicit list
  of verified / unmet conditions.
- It carries a privacy notice stating that no exact income or financial history
  appears on it, and a generated-at timestamp in UTC.
- **Print / Save PDF** calls `window.print()` (`EligibilityCertificate.tsx:111`)
  — it is a browser print dialog, not a bundled PDF library.

> The certificate is generated **locally in the browser** from the in-memory
> outcome object. It is a record of the result, not a signed or on-chain
> attestation.

---

## 10. Privacy Dashboard

Open the **Privacy** dashboard tab, or the **Privacy** nav item for the public
privacy page.

The **Privacy Dashboard** (`PrivacyDashboard.tsx`) is a two-column comparison:

| PRIVATE — *never shared* | VERIFIED RESULT — *can be verified* |
| --- | --- |
| Exact income | Eligibility result |
| Financial history | Verification status |
| Personal information | Proof / reference |

Both columns change their status line with state: the private side says *"Used on
your device to compute the result — never revealed"* once a wallet is connected,
and the result side says *"A verified result is ready to share — with no exact
income figures"* once a verification has produced an outcome.

This view is honest about its scope: it describes the split between private
inputs and disclosed outcomes. It does not claim that the browser flow produced
an on-chain proof.

## 12. Troubleshooting

### The wallet is not connected / "Wallet not detected"

- The browser cannot see the wallet extension. Confirm 1AM Wallet (or Lace) is
  installed **in the same browser profile** you are running the app in, is
  unlocked, and that the page was loaded **after** the extension was installed
  or enabled. `detectWallet()` reads `window.midnight` at click time
  (`wallet.ts:56-62`); if the extension injected nothing, it returns
  `undefined`.
- The error card shows a **Wallet not detected** heading with **Install Wallet**
  (which opens `https://docs.midnight.network/relnotes/lace`) and **Try Again**
  buttons (`WalletStatus.tsx:137-151`).
- **"Connection cancelled"** means the approval popup was rejected. The app
  surfaces this as a `rejected` state and never fabricates an address
  (`wallet.ts:151-153`); press **Try Again** and approve.
- If the wallet approves but a later call hangs, the app gives the wallet a
  **20-second budget** per call and then reports *"The wallet did not respond in
  time."* as a `connection-error` (`wallet.ts:97-109`). This bounds the wait; it
  does not substitute any data.
- If the connection is lost after approval, you get a `disconnected` error
  (*"The wallet connection was lost."*, `wallet.ts:167-169`).

### Wrong network

- The wallet is on something other than Preprod. The app throws
  `wrong-network` and names the network it actually saw
  (`wallet.ts:171-177`), and the UI shows a **Wrong network** error card
  (`WalletStatus.tsx:162-171`).
- Fix: switch the network **inside 1AM Wallet** to Midnight Preprod, then press
  **Try Again**. The `Preprod` pill in the navbar
  (`Navbar.tsx:63`) indicates the network CrediFi expects, not the live state.
- A useful detail: the network check happens on the reported
  `getConnectionStatus()` result. If that status read fails, the app falls back
  to assuming the requested network rather than blocking the user
  (`wallet.ts:162-166`) — so if you are unsure, confirm the network in the wallet
  itself.

### API or connection issue

- **"Connection failed"** is the catch-all branch of the wallet error card
  (`WalletStatus.tsx:172-181`) and wraps any unexpected error from `connect()`.
  Press **Try Again**; if it persists, reload the page and confirm the extension
  is still enabled.
- **The app is blank or the flow will not advance.** CrediFi needs its generated
  contract artifacts. On a fresh clone run `npm run contract:compile` before
  `npm run frontend:dev`; `frontend/src/engine.ts` imports `CrediFi` and
  `witnesses` from the `credifi-contract` workspace, so missing managed
  bindings will break the engine.
- **"Connecting…" never resolves.** That is the `withTimeout` case above (20 s
  per call). Reload and re-approve.
- **Wallet says connected but the app still shows the Connect button.** The
  navbar and the app state are driven by the single `WalletState` in
  `App.tsx:46`; press **Connect wallet** again, or reload so the extension
  re-injects.

### Transaction or verification failure

- The **Check Eligibility** button is disabled with the label *"Connect wallet to
  continue"* until a wallet is connected (`VerificationStatus.tsx:80-82`). If
  you see that, the problem is connection, not verification.
- If the verification engine throws, the app returns to the verification screen
  and shows an error card titled *"Verification could not be completed"* with
  the engine's own message, a **Why** line, and a **Next** line, plus a **Try
  Again** button (`VerificationStatus.tsx:86-97`; also `App.tsx:155-159`).
- A specific engine failure looks like *"CrediFi engine: verification record N
  not found in ledger"* (`engine.ts:127`) — the compiled contract ran but the
  expected record was not in the read-back. Reload the page (a fresh
  `CrediFiEngine` resets its result counter) and re-run.
- **Result is "Not Eligible".** This is a real outcome, not a failure. Compare
  the *Your requirement* minimum income against the *Your Financial Details*
  monthly income, and check whether *Previous Loan Default?* is set to **Yes**
  while the requirement asks for no prior default. Adjust the input — editing any
  field clears the current outcome (`App.tsx:270-288`) — and re-run.

## Known limitations

These are properties of the current build, confirmed by reading the source.

1. **The verification runs in-process, not on-chain.** The browser executes the
   compiled contract locally (`frontend/src/engine.ts`, `DEMO_MODE = true` in
   `frontend/src/config.ts`). No ZK proof is generated and no transaction is
   broadcast from the app. The *"Waiting for blockchain confirmation…"* phase is
   a UI state, not a network wait. There is **no network traffic at all** in the
   browser flow — `fetch`, `XMLHttpRequest`, `axios` and `WebSocket` do not
   appear anywhere in `frontend/src/`.
2. **The *"Generate Proof"* step label is aspirational in the browser flow.** The
   result comes from the contract package's vanilla execution path, not a proof
   server. Submitting the verification as an on-chain transaction from the browser
   is listed as **deferred** in the README roadmap.
3. **Verification history is session-only.** `localStorage`, `sessionStorage` and
   `indexedDB` do not appear anywhere in `frontend/src/`. Reloading the page
   loses every result. (See [Verification History](#8-verification-history).)
4. **The issuer is a mock.** Credentials are signed by a deterministic mock
   issuer (`MOCK_ISSUER_NAME` in `frontend/src/config.ts`). Running it as a real
   trusted service is on the roadmap.
5. **There is no in-app feedback submission and no analytics.** No feedback form,
   no feedback endpoint, no telemetry. The Level 5 feedback round was collected
   entirely through the external Google Form.
6. **No numeric risk score exists.** The contract produces only boolean
   outcomes. `lib/eligibility.ts` derives a plain-language category and
   deliberately never invents a score, despite the component being named
   `RiskScore.tsx`.
7. **Addresses are shown in truncated form only.** The navbar and history show a
   shortened address, and the certificate shows a 16-character holder-hash
   prefix. A full address is never rendered in a result.
